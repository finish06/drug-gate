## 1. Overview

Establish a repeatable, audited production deployment workflow for drug-gate. Today, staging deploys happen via push-to-main → `:beta` image build → webhook + cron-fallback. Production has no automation — tagged releases (`:vX.Y.Z`, `:latest`) build but there's no documented promote-to-prod step, no health gate, no rollback procedure.

### User Story

As **the operator of drug-gate**, I want **a one-button production deploy that verifies health before promoting and supports one-command rollback**, so that **I can ship releases without coordination overhead and recover from a bad deploy in seconds**.

## 2. Problem

Current state (from `docs/staging-deployment.md` and CI workflows):

- Tagged releases produce `:vX.Y.Z` + `:latest` images. No production environment consumes them automatically.
- Production runs "Self-hosted, behind firewall, same network as cash-drugs" (CLAUDE.md). The actual deploy mechanism for prod is undocumented.
- The PRD declares M9.5 production deploy as the gating work for beta → GA promotion (alongside M10 admin auth hardening).
- The promotion ladder in `.claude/rules/environment-awareness.md` says production deploys must be human-approved.

Gap: no documented production deploy command, no health gate, no rollback runbook, no audit trail.

## 7. Open Questions for Human (must resolve before v1.0)

- **Q1 (architecture):** Is the production host the same machine as staging (`192.168.1.145`), a different homelab box, or a cloud VM? "Self-hosted, behind firewall" is vague.
- **Q2 (trigger):** What initiates a prod deploy — `workflow_dispatch`, git tag push, PR merge with label, or manual SSH? See AC-002.
- **Q3 (traffic shifting):** Is there a load balancer in front of drug-gate prod, or does deploy = restart the single container? This determines whether the health gate can do blue/green or only rolling restart.
- **Q4 (rollback semantics):** Auto-rollback on health-gate failure, or always-human-approved rollback? See AC-008.
- **Q5 (state during deploy):** Is Redis the same instance across deploys (state persists) or does each deploy spin up a fresh Redis? Affects rollback simplicity.
- **Q6 (DNS):** `drug-gate.calebdunn.tech` — Cloudflare-proxied? Is DNS swapping part of the deploy or fixed forever?
- **Q7 (audit / observability):** Is GH Actions run history enough, or do we want deploy events posted to a Slack/Discord channel?
- **Q8 (rollout cadence):** How often do you expect to deploy prod? Daily, weekly, on-feature-complete? This affects how much automation effort is justified.

## 8. Edge Cases (preliminary — confirm during interview)

- Tag exists but image build failed → deploy workflow should detect and abort with a clear error.
- Tag exists, image built, but cash-drugs upstream is also down → health gate's circuit-breaker check returns `degraded` (not failed). Does that pass or block?
- Concurrent deploy attempts (two operators trigger at the same time) → workflow concurrency group should serialize or reject.
- Deploy succeeds but a downstream dependency (Redis) fails 5 minutes later → outside the deploy gate, falls to alerting (not M9.5's concern).

## 9. Out of Scope

- Multi-region or multi-AZ failover (not in beta → GA scope).
- Database migrations / Redis schema changes (drug-gate is stateless above Redis; no schema).
- Cost / capacity planning.
- M10 admin auth hardening — separate milestone.
